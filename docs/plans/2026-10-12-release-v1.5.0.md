# Release v1.5.0

Status: **In Progress**
Approved date: **2026-10-12**
Approved target: **stable GitHub Release `v1.5.0`**
Baseline branch/commit: **`remote` / `e152c9d4c5fe203c94682279b1fa9ab7cf9c6620`**

## Objective

Publish the current user-accepted RC2 behavior as stable version `1.5.0` so
installed `v1.4.0` workstations can discover, download, and install the update.
Operational stability takes priority; deeper dependency, network-exposure,
formatting, and security remediation is deferred to a separately approved
follow-up release.

## Approved Scope

- Promote version metadata from `1.5.0-rc.2` to `1.5.0` across active package,
  API, release, and current-project documentation metadata.
- Preserve historical RC1/RC2 plan and artifact references as historical facts.
- Include the already reviewed documentation refresh in the release commit.
- Run the approved non-hardware release verification gates.
- Build and inspect a local `1.5.0` Windows installer.
- Commit the release state, push branch `remote`, create and push tag `v1.5.0`.
- Monitor the Windows Setup GitHub Actions workflow and verify the stable GitHub
  Release assets used by `electron-updater`.

## Non-goals

- No functional change to authentication, remembered login, Dongil, PLC,
  camera, ROI, installer behavior, or updater behavior.
- No dependency upgrade or automatic `npm audit fix`.
- No change under `tool/`, protected license source/binaries, or Dongil Server.
- No database migration or seed change.
- No hardware flow or production database write during release preparation.

## Accepted Residual Risks

- Next.js and other dependency advisories remain unresolved for this release.
- Packaged Next.js and Device Tool network-binding hardening is deferred.
- The fixed PostgreSQL bootstrap superuser credential is deferred.
- Frontend hook lint and backend mixed-line-ending lint findings remain.
- Private Tool download reliability depends on GitHub/CDN availability; the CI
  workflow must still verify the pinned private asset and its checksum.

## Rollback And Stop Conditions

- Stop before commit/tag when tests, typecheck, build, runtime staging, protected
  boundaries, version consistency, or installer inspection fails.
- Stop after branch push but before tag if the pushed commit cannot be verified.
- If the tag workflow fails, do not alter `v1.4.0`; diagnose and repair the same
  `v1.5.0` workflow only after confirming no valid release was published.
- Do not delete, overwrite, or retag a published release without separate
  destructive-action approval.
- The updater checkpoint/rollback path remains responsible for recovery on an
  installed workstation; target-machine update acceptance remains separate.
